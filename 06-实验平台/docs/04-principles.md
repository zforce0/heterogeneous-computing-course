# 04 · 相关原理（对照课堂概念）

本文把工程里的实现映射到课程概念。**结论只引用已归档实测**；未测项按归档口径标 `N/A`。

## 4.1 异构分工：把任务放到合适的算力上

| 任务 | 节点 | 为什么 |
|---|---|---|
| 显示/控制 | Mac M1 | 有屏幕与交互；M1 虽曾是 LLM 最强节点，但课程架构要求它退出推理 |
| 中心 LLM | 昇腾盒子（ARM CPU） | 24 GB 内存装得下 0.6B Q4；提供 OpenAI 兼容 API；NPU 算子库不完整，不能用 |
| 视觉推理 | RV1126B NPU | 2 TOPS INT8 + 相机直连，避免把视频流搬上网络 |
| 二次确认 | RK3588 | 有 NPU/CPU/GPU 余量；G3 阶段做规则复核，G4 阶段跨板调用昇腾 LLM |

关键认识：**TOPS 不等于 LLM 能力**。自回归解码受内存容量/带宽约束。M1 实测 8.2B Q4 为 9.3–9.53 tok/s；昇腾 310B1 虽有 20 TOPS，但 LLM 栈不可跑（CANN 8.0.RC3 缺 RmsNorm/RoPE/fp16 NZ matmul），实测吞吐 N/A。G4 的决策是把 0.6B 放昇腾 ARM CPU（3/3 用例中位 4.04 tok/s），以够用的语义能力换跨设备协同的可观察性。

## 4.2 互联与通信：从链路上行到应用层协议

**拓扑**：早期是 RV→RK 链式（eth0 + 三层转发 + proxy ARP）；后改为交换机星型 `192.168.77.0/24`。链式遗留的 proxy ARP 曾把 `.22` 的流量劫持到 RK 的 eth1（已 down），症状是 100% 丢包——这是「网络层配置影响应用层可达性」的典型案例。

**G3 长度前缀证据协议**（`evidence_sender.py` / `evidence_server.py`）：

- 帧格式：4 字节大端长度 + UTF-8 JSON；字段含 `run_id, node, event_id, model, model_version, deadline_ms, seq, infer_ms, detections[]`；
- 幂等：以 `(run_id, event_id)` 去重，重发返回缓存 ACK 并计 `duplicate`；
- 期限：各端墙钟漂移可达数月，因此用**单调钟测 RTT ×5、下限 200 ms**建 deadline，不依赖绝对时间；
- 重试：最多 3 次，同一 event_id 幂等重发。

实测（20 s，千兆直连）：unique 164/164、ACK 164/164、duplicate 0、RTT 中位 0.82 ms。链路受限实验（100 ms 时延 + 15% ACK 丢包 + 120 ms 期限）：sent 104、unique 93、重试 11、duplicate 11，双端对账一致——**at-least-once + 幂等**做到了不重不漏。内核缺 `sch_netem`，时延用接收端应用层仿真，这是如实标注的实验方法妥协。

## 4.3 体系结构与 Roofline

Roofline 的核心是「算术强度 vs 内存带宽/峰值算力」：

- **LLM decode**：每生成一个 token 都要把权重扫一遍，算术强度低，落在**带宽屋顶**下。0.6B Q4 GGUF ≈499 MB，选择它是为了在 4×TAISHAN @1.6 GHz 上取得可用延迟；盒子 24 GB 允许更大模型，但算子库不支持。
- **RK3588 推理**：NPU `mobilenet_v1.rknn` INT8 实测 2.30 ms/次（430 FPS，Core0 ~80%）；CPU OpenCV GEMM 2.4 GFLOPS；GPU OpenCL GEMM 1624 GFLOPS（约为 CPU 的 677 倍）但小卷积因搬运开销反而不如 CPU（6.9 vs 9.2 GFLOPS）。这正说明**峰值算力与实际算子/搬运开销的差距**。
- **ResNet-50 量化**：ONNX FP32 on CPU 122 ms（8.2 FPS，7.5 核）→ 自转 RKNN FP16 NPU 32.6 ms（~30 FPS），约 3.7×；INT8 理论上可到 ~10 ms（归档标注为官方数据，不是本实验实测）。

## 4.4 并行编程与流水线调度

一条观测流水线有 5 段：

```
采集(5 fps IR / 7.5 fps VIS) → 端侧推理(NPU) → 打包/传输(TCP) → 二次确认(RK/LLM) → 聚合显示(SSE)
```

- NPU 是共享资源：`yolo_live` 单帧约 77 ms，`ir_detect` 含上采样与映射约 110–130 ms。两者同时跑会排队，因此热成像网络推理**每 2 帧一次**（≈2.5 Hz），传统热斑逐帧（≈5 Hz）；实测可见光仍 7.5 fps，无堆积。
- 帧新鲜度用 `st_mtim.tv_nsec + size` 判定：秒级 `mtime` 会把检测钉死在 1 Hz；同帧重复推送会让 `ir_fps` 虚高（6.5 → 修正后 5.0）。
- 证据协议用 RTT deadline 串起两端，避免慢节点拖垮整条流水线；策略化载荷压缩（`person` / `roi_top1`）在事件数不变时把出向字节降 24.1% / 22.4%。

## 4.5 模型量化与短策推理

- **Q4 GGUF**：0.6B 权重压到 499 MB，适配盒子的 ARM CPU 与内存带宽；代价是语义能力有限，页面明示其结论仅供参考。
- **INT8 / FP16 RKNN**：RV1126B NPU 只跑 INT8/量化模型；热成像复用可见光 `yolov8m_rv1126b.rknn`（256×192 → 640×480 等比放大，同 4:3 无形变）。跨模态导致分数普遍偏低、整窗漏检常见——这是**待测的物理现象**，工程把它量化为「分差 / 命中率差」而不是掩盖。
- **短上下文/短输出**：课堂 LLM 对话限制 `max_tokens`，研判只有三行。0.6B 的提示词行为经实测：模板行带可执行文字（「从正常/关注/异常里选…」）会被整段照抄；只有三字占位（「理由：一句话」）才会替换，且约 1/3 概率不替换。因此判据写在后端、判断行由后端强制回填，理由/建议失败时最多重试 3 次并如实降级。

## 4.6 性能评估与试验方法论

- **用命令输出作证据**：`ping` 判定用退出码或 `\b0\.0% packet loss` 正则——裸子串 `"0.0% packet loss"` 会被 `"100.0% packet loss"` 命中，历史脚本因此误报过 PASS。
- **区分事件与稳态**：事件只记状态边沿。进入需连续 2 个采样命中，离开需连续 8 s 未检出，分数 <0.40 的弱检测只进「当前稳态」；否则 YOLO 抖动会刷屏。
- **区分统计口径**：同一帧重复推送不能算两帧；归档关键帧标 `archived`，实时流标 live；N/A 不填 0。
- **统一 run_id**：G3/G4 归档以时间戳 run_id 命名，含 report.md、manifest、checksums，可对账、可回放。
- **拓扑可观测性**：交换机不可管，端口对端只能标 `inferred`；用 `driver + sysfs 总线` 判介质（如 `r8152 + usb` → USB 网卡），不用「看起来像」来填图。

## 4.7 接地问答（Grounded QA）

对话默认注入实时事实（可用 `"ground": false` 关闭）：

```
节点名单（/api/roster，25 s 缓存）   → 问「谁在跑什么」
事件台账（/api/events，2 s 采样）   → 问「近一分钟有哪些事件」
窗口证据 + 后端对比行              → 问「双光研判」
```

事实与措辞分离：**数字只能来自后端，LLM 只负责组织语言**。事件列举按 n=0/1/>1 分支给不同模板；研判的「判断」行由 `verdict()` 机械计算并在返回前无条件覆盖。这样 0.6B 的不可靠性被限制在措辞层，不影响结论的可核对性。
