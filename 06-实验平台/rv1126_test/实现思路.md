# RV1126B 可见光摄像头 YOLOv8 实时推理 — 实现思路

> 目标:在 RV1126B(EASY-EAI-NANO-TB,`root@192.168.3.248`)上,从可见光 USB 摄像头持续取流,每次取**最新一帧**送 YOLOv8m RKNN 模型推理,打印每帧处理耗时;检出目标时画框标注、打印结果、保存标注图,且磁盘只保留最近 10 张结果图。rknn 模型路径作为命令行参数传入(与 `yolov8_detect_C_demo` 用法一致)。

| H264 | 1920×1080 / 1280×720 / 640×480 |

### 1.3 参考项目分析结论

**A. `yolov8_detect_C_demo`(RV1126B 单图推理 demo,直接复用其推理链路)**

- `lib/yolov8.cpp`:`yolov8_detect_init()` 内存方式 `rknn_init` → 查询输入输出属性 → 判定 int8 量化;`yolov8_detect_run()` letterbox 预处理 → `rknn_inputs_set`(UINT8/NHWC,非零拷贝)→ `rknn_run` → 量化输出直接取 int8(`want_float=0`)→ 后处理。
- `lib/yolov8_postprocess.cpp`:YOLOv8 三层输出(stride 8/16/32)、DFL softmax 解码、按类 NMS(BOX_THRESH=0.45 之外的 conf 0.25、NMS 0.45)、COCO 80 类名硬编码。
- `include/`:本地自带 `rknn_api.h` / `postprocess.h` / `yolov8.h` / `file_utils.h`,无需 SDK 安装即可编译。
- 模型:`yolov8_detect_demo_release/yolov8m_rv1126b.rknn`(量化版,输入 640×640)。
- 构建:`CMakeLists.txt` + `build.sh`,依赖外部工具链文件 `~/configs/cross.cmake` —— **该文件在本机已缺失**(未随共享目录同步),需自建(见 §5)。
- 已知小坑:demo main 里硬编码读 `test.jpg`(忽略 argv[2]);letterbox 填充为黑色。新代码不沿用 main,只复用 lib。

**B. `twocameraOnMAC`(可见光 V4L2 采集参考,直接复用其采集模块)**

- `src/visible_camera.{h,cpp}`:纯 V4L2 API —— sysfs 遍历 `/sys/class/video4linux/*` 按 VID/PID(逐级向上找 `idVendor/idProduct`)探测设备 → `open(O_RDWR|O_NONBLOCK)` → `VIDIOC_S_FMT`(MJPG/分辨率)+ `VIDIOC_S_PARM`(帧率)→ `VIDIOC_REQBUFS`(4 个 MMAP 缓冲)→ `STREAMON` → 独立采集线程 `poll(250ms)`+`DQBUF/QBUF` 循环 → `latest_frame_` 互斥锁保护,消费者 `copy_latest()` 拿最新帧。**这正是"每次取视频流最新图片"的现成实现。**
- `src/mjpeg_decoder.{h,cpp}` + `mjpeg_huffman_tables.h`:libjpeg `jpeg_mem_src` 解 MJPG 为 BGR24,并补齐 UVC 摄像头常缺的标准 Huffman 表。
- 命令行支持 `--width/--height/--fps` 覆盖,驱动就近协商、读回实际值(`actual_width_/height_`)。

## 2. 总体架构

```
                 ┌────────────────────────────────────────────────┐
                 │              主线程(推理循环)                  │
                 │  copy_latest() → 计时 → letterbox+rknn_run     │
                 │  → 后处理 → 打印耗时/结果 → 画框 → 存图(留10张)│
                 └───────────────────▲────────────────────────────┘
                                     │ latest_frame_(mutex)
┌──────────────┐  MJPG帧  ┌──────────┴─────────┐
│ USB 摄像头    │ ───────▶ │ 采集线程(V4L2)     │
│ 1d6c:0103    │  UVC     │ poll→DQBUF→libjpeg │→ BGR Mat
└──────────────┘          │ 解码→存最新帧→QBUF  │
                          └────────────────────┘
```

两个关键设计:

1. **采集与推理解耦(双线程)**:采集线程全速运行,始终用最新帧覆盖 `latest_frame_`;主线程每次推理完成后才取下一张最新帧。这样即使推理慢(丢帧),也不会积压旧帧、处理滞后。
2. **复用成熟代码**:推理链路整体拷贝 `yolov8_detect_C_demo/lib` + `include`;采集链路拷贝 `twocameraOnMAC` 的 `visible_camera` + `mjpeg_decoder`(剥离红外/配准/跟踪/显示等无关部分,仅做必要的接口适配)。新写的只有 `main.cpp`(参数解析 + 主循环 + 计时 + 标注 + 存图管理)。

## 4. 模块设计

### 4.1 采集模块(复用 visible_camera,小改)

- 保留:VID/PID(1d6c:0103)sysfs 自动探测 + 节点可由命令行覆盖;MJPG/YUYV 可选;分辨率/帧率可配;MMAP 4 缓冲;独立采集线程;`copy_latest()` 取最新帧。
- 调整:去掉与红外/同步器相关的依赖,`BgrFrame` 直接转成 `cv::Mat`(浅拷 data 指针即可,两者都是连续 BGR24)。
- **计时扩展**:采集线程为每帧记录 `cap_wait`(poll 等待时长)、`dec_ms`(MJPG→BGR 解码耗时)与解码完成时刻 `t_ready`,随帧传递给主线程,供全链路计时使用(见 4.7)。
- 兜底:VID/PID 匹配失败时回退任意支持 MJPG 的采集节点并打印告警(参考项目原逻辑,应对设备识别异常)。

### 4.2 推理模块(复用 yolov8 lib,加全链路分段计时)

- `yolov8_detect_init(model_path, &ctx)`:从命令行传入的 rknn 路径加载(满足"模型作为命令行参数"的需求,用法与 demo 一致:`./rv1126_yolov8_demo yolov8m_rv1126b.rknn ...`)。
- `yolov8_detect_run(ctx, image, results)`:内部完成 letterbox、输入设置、`rknn_run`、int8 后处理、坐标逆映射回原图。
- **全链路分段计时**:在 `yolov8_detect_run` 内部对 5 个阶段分别计时(预处理 / 输入提交 / NPU 推理 / 输出取回 / 后处理),通过新增输出参数 `double stage_ms[5]` 带回 main(不改变原有推理行为);main 补上总耗时并统一打印,作为芯片性能基准,详见 4.7。

### 4.3 主循环(main.cpp 新写)

```text
解析参数(模型路径必须;相机参数可选)
yolov8_detect_init(model)
VisibleCamera open + start(后台持续刷新 latest_frame)
loop:
    frame = camera.copy_latest()            // 每次拿最新帧,帧自带 cap/dec/t_ready
    age = now - frame.t_ready
    yolov8_detect_run(ctx, frame, results, stage_ms)  // 记录 pre/set/npu/get/post
    infer = sum(stage_ms)
    if !results.empty():
        t0 = now
        画框 → 保存 output/det_*.jpg → 滚动清理(只留 10 张)
        save = now - t0
    total = (save 完成或 post 完成) - frame.t_cap   // 端到端
    printf("[PERF] #n cap=.. dec=.. age=.. pre=.. set=.. npu=.. get=.. post=.. infer=.. save=.. total=.. fps=.. obj=..")
    for r in results:
        printf("  %s %.2f%% @ [x1,y1,x2,y2]")   // 类名/置信度/坐标
    (无目标不保存图片,save=0,继续下一轮)
Ctrl+C / SIGINT → 优雅退出:停采集线程、rknn_destroy、打印 [STAT] 统计(见 4.7)
```

### 4.4 结果图管理(只留最近 10 张)

- 保存目录:`--save-dir` 指定,默认 `./output`,启动时自动创建。
- 文件名内嵌毫秒时间戳保证字典序 = 时间序:`det_20260920_153000_123.jpg`,清理时只需 `readdir` + 排序 + `unlink` 最旧的,无需额外状态文件。
- 只在**检出目标**时保存(按需求"图片中有识别到的物体…保存相关的图片")。

### 4.6 Ctrl+C 优雅退出

程序必须能通过 **Ctrl+C(SIGINT)** 随时安全退出,不做资源泄漏、不残留占用的相机设备。设计如下:

**机制**

- main 入口处尽早用 `sigaction` 注册 `SIGINT` 与 `SIGTERM`(SIGTERM 兼顾 `kill`/systemd 停止场景)。
- 信号处理函数**只做一件事**:置 `std::atomic<bool> g_running = false`(async-signal-safe,绝不在 handler 里做打印/释放等复杂操作)。
- 主循环每次迭代开始检查 `g_running`,为 false 则跳出循环进入清理流程。
- 连按两次 Ctrl+C 兜底:第二次触发时恢复默认 handler(`SIG_DFL`),允许用户强制终止(防止卡死时无法退出)。

**清理流程(退出时顺序执行)**

```text
跳出主循环
 1. 停止相机:camera.stop()  → 独立采集线程 join → VIDIOC_STREAMOFF → munmap → close(fd)
 2. 释放模型:yolov8_detect_release(&ctx) → rknn_destroy
 3. 打印统计:总帧数、平均/最大单帧耗时、检出帧数、已保存图片数
 4. return 0
```

**几个边界情况的处理**

- **采集线程阻塞在 `poll()`**:poll 本身用 250ms 超时循环,stop() 置停止标志后线程最多 250ms 内自行退出并 join,无需特殊处理(不需要 close fd 打断)。
- **主线程阻塞在 `rknn_run()`**:推理是同步调用,当前这一帧跑完后才检查到标志位退出,最多多处理一帧,可接受。
- **启动阶段(相机打开前/模型加载中)按 Ctrl+C**:handler 在 main 最开始就注册,清理函数对"未初始化的资源"均判空跳过,任意阶段退出都安全。
- **退出码**:正常 Ctrl+C 退出返回 0;若因相机打开失败等错误退出,返回非 0 并打印原因。

### 4.7 全链路计时与性能基准输出

以每帧处理耗时为芯片/管线性能分析基准,覆盖**相机采集 → 格式转换 → YOLO 推理 → 图片存储**完整流程:

**计时点划分(全链路 4 大阶段 + 端到端)**

| 段 | 计时范围 | 测量位置 | 含义 |
|---|---|---|---|
| `cap` | 进入 poll() → DQBUF 拿到 MJPG 数据 | 采集线程 | 等待相机出一帧的时长(≈帧间隔,反映相机出帧节奏) |
| `dec` | DQBUF 完成 → BGR 帧就绪 | 采集线程 | **格式转换**:MJPG→BGR 解码耗时 |
| `age` | 主线程取帧时刻 − 解码完成时刻 | 主线程 | 帧龄:帧在缓冲里等了多久,衡量"取最新帧"的新鲜度 |
| `pre` | letter_box() 进入到返回 | 推理函数 | CPU 预处理(缩放+填充) |
| `set` | rknn_inputs_set() | 推理函数 | 输入提交(含驱动侧拷贝/量化) |
| `npu` | rknn_run() | 推理函数 | **NPU 纯推理(芯片性能核心指标)** |
| `get` | rknn_outputs_get() | 推理函数 | 输出取回 |
| `post` | post_process()+scale_coords() | 推理函数 | CPU 后处理(DFL 解码+NMS+坐标逆映射) |
| `infer` | pre+set+npu+get+post 之和 | 主线程 | 推理全段合计 |
| `save` | 画框+JPG 编码+写盘 | 主线程 | 仅检出帧统计,未检出帧记 0 |
| `total` | DQBUF 完成 → 存盘完成(未检出帧到 post 完成) | — | **端到端**:一帧从相机到落盘的完整时长 |

- 计时时钟:`clock_gettime(CLOCK_MONOTONIC_RAW)`(单调、不受 NTP/调频影响,适合性能测量),封装为 `double now_ms()` 工具函数。
- 实现方式:
  - 采集线程在 `BgrFrame` 已有时间戳基础上,新增携带 `cap_wait`、`dec_ms` 与解码完成时刻 `t_ready`,随帧传给主线程;主线程取帧时算出 `age`。
  - 推理 5 段计时在 `yolov8.cpp` 的 `yolov8_detect_run` 内部完成,签名增加输出参数 `double stage_ms[5]`(不改变原有推理行为);main 汇总 `infer`/`total` 并统一打印与累计统计。

**每帧输出格式(单行固定字段,按管线顺序排列,便于 grep/awk/导入表格分析)**

```
[PERF] #123 cap=31.2 dec=5.8 age=0.4 pre=2.1 set=0.5 npu=28.7 get=1.2 post=12.4 infer=44.9 save=3.2 total=85.5 fps=11.7 obj=3
```

- `fps` = 1000 / 最近一次 total(瞬时值);`obj` = 本帧检出目标数。
- 分析口诀:`total ≈ cap 之外的时间`;`age` 大说明推理太慢跟不上采集;`dec` 大说明解码是瓶颈(可降分辨率);`npu` 看芯片,`pre/post` 看 CPU。

**运行汇总(Ctrl+C 退出时打印)**

```
[STAT] frames=520 obj_frames=87 saved=10
[STAT] total  ms: avg=85.5 min=83.1 max=99.6 p95=88.0
[STAT] npu    ms: avg=28.5 min=27.9 max=31.2 p95=29.4
[STAT] avg: cap=31.2 dec=5.8 age=3.1 pre=2.1 set=0.5 get=1.2 post=12.4 save=3.2
```

- 对 total 与 npu 两个关键指标给出 avg/min/max/p95(p95 用简单排序法);cap/dec/age 及推理各段给 avg。
- 该汇总即性能基准报告:对比不同模型、量化方式、核频、采集分辨率时,只需对比各阶段 avg。

## 5. 构建与部署方案

**现状**:本机有 `aarch64-linux-gnu-gcc/g++(15)`(Ubuntu 交叉工具链),但原 demo 依赖的 `~/configs/cross.cmake` sysroot 已缺失;**而板上 g++ 13.3 + OpenCV/libjpeg/rknnrt 开发文件齐全,可直接编译**。

因此 CMakeLists 采用**双模式**:

1. **板端编译(首选,零环境搭建)**:
   ```bash
   # 源码 scp/rsync 到板(或经 hgfs),板上执行:
   cd rv1126_test && ./build.sh        # cmake -B build && make
   ./build/rv1126_yolov8_demo yolov8m_rv1126b.rknn
   ```
   - `build.sh` 检测 `uname -m == aarch64` 时直接本机编译;板端链接 `/usr/lib/librknnrt.so`(2.3.2)与 OpenCV 4.6,全部现成。
   - 缺点:每次改码要同步源码;板端编译稍慢(本工程规模小,可接受)。

2. **本机交叉编译(备选,需一次性搭 sysroot)**:
   - `cmake -DCMAKE_TOOLCHAIN_FILE=$HOME/configs/cross.cmake ..`;`cross.cmake` 内容:
     ```cmake
     set(CMAKE_SYSTEM_NAME Linux)
     set(CMAKE_SYSTEM_PROCESSOR aarch64)
     set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
     set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
     set(CMAKE_SYSROOT  $ENV{HOME}/sysroots/rv1126b)   # 见下
     set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
     set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
     ```
   - sysroot 一次性制作(脚本 `make_sysroot.sh` 自动完成):
     ```bash
     # 从板端拉取开发文件(仅头文件+so,百 MB 以内)
     rsync -avL root@192.168.3.248:/usr/include      ~/sysroots/rv1126b/usr/
     rsync -avL root@192.168.3.248:/usr/lib          ~/sysroots/rv1126b/usr/   # 可仅拉 libopencv_core/imgproc/imgcodecs、librknnrt、libjpeg
     rsync -avL root@192.168.3.248:/lib/aarch64-linux-gnu ~/sysroots/rv1126b/lib/  # 动态链接器/loader
     ```
   - 注意:本机交叉 gcc 为 15,板端运行库由 Ubuntu 24.04(gcc13)提供,`libstdc++` ABI 向后兼容,无问题;链接时 `-Wl,--dynamic-linker=/lib/ld-linux-aarch64.so.1` 已由 sysroot 覆盖。

## 11. 三线程总体架构

```
┌──────────────┐ raw ISO USB        ┌──────────────────────────┐
│ IR 模组       │ ◀──────────────── │ IR 采集线程               │
│ 0bda:5840    │  libusb+闭源 SDK  │ uvc_frame_get 拉帧        │
│ (不用V4L2)   │                   │ raw_data_cut→YUYV→RGB→BGR│
└──────────────┘                   │ →覆盖 ir_latest→帧计数   │
                                   │ SDK 自行管理 USB 传输     │
                                   └──────────────────────────┘
┌──────────────┐  MJPG 1280x720@25  ┌──────────────────────┐
│ 可见光相机    │ ────────────────▶ │ VIS 采集线程(V4L2)    │
│ 1d6c:0103    │   UVC             │ poll→DQBUF→libjpeg    │
└──────────────┘                   │ →覆盖 vis_latest→QBUF │
                                   │ →帧计数/时间戳        │
                                   └──────────▲───────────┘
                                              │ copy_latest()
                            ┌─────────────────┴────────────────┐
                            │ 主线程(推理循环,~14fps)          │
                            │ 取 vis 最新帧 → yolov8_detect_run │
                            │ →打印 infer 耗时/检出明细         │
                            │ →画框存图(留10张)                 │
                            │ 每 2s 打印两路 [FPS]             │
                            └──────────────────────────────────┘
```

要点:

- 三个执行流互不阻塞:两路采集只做"解码 + 覆盖最新帧 + 计数",主线程的慢推理不影响任何一路采集;
- 红外帧**不需要被主线程消费**,帧率统计在 IR 采集线程内部完成(主线程只读计数器),因此即使主线程忙,IR 统计也持续准确;
- 不做双路帧同步/配准(本期无融合需求),去掉 synchronizer 概念。

## 12. 实际采样帧率统计(本期核心输出)

### 12.1 采集类内增加轻量计数器

在两个采集类(`IrCamera`、`VisibleCamera`)中增加**同名的帧率计数接口**:

```cpp
struct FrameRateInfo {
    uint64_t total_count;   // 成功解码并发布的累计帧数
    double   start_ms;      // 计数起点(now_ms())
    double   window_fps;    // 最近 2s 窗口帧率
    double   avg_fps;       // 从启动至今平均帧率
};
```

- 采集线程**每成功发布一帧**(成功覆盖 latest 之后)执行 `++published_count_`;IR 的计数点在 `process_image_frame()` 成功末尾,VIS 在解码 swap 之后;
- 采用"最近窗口环形计数":维护最近 2 秒内帧到达时刻的简单环形缓冲(或等价的双计数槽),`window_fps = 窗口内帧数 / 2.0`;
- `avg_fps = total_count / (now_ms()-start_ms) * 1000`;
- 统计基于 `CLOCK_MONOTONIC_RAW`,相机重连/时间戳异常不影响(计数发生在发布成功点,与相机自带时间戳无关)。

### 12.2 周期性打印(替代刷屏的逐帧 PERF)

主线程每轮推理后检查距上次 FPS 打印是否 ≥ 2 秒,到点则输出一行:

```
[FPS] ir : cur=25.0 avg=24.9 (frames=2150) | vis: cur=24.5 avg=24.8 (frames=2128)
```

- `cur` = 最近 2s 窗口实测帧率(保留 1 位小数),这是判断两路是否达标(IR 25 / VIS 25)的直接依据;
- 首行在启动 2 秒后打印;程序运行不足 2 秒退出时只打退出汇总。

### 12.3 退出汇总(Ctrl+C)

```
[STAT] ir  frames=3125  avg_fps=25.0
[STAT] vis frames=3090  avg_fps=24.7
[STAT] infer count=430 avg=71.3ms   obj_frames=61 saved_pairs=10
[STAT] save avg=4.6ms max=7.1ms   align_delta avg=9ms max=18ms
```

### 12.4 双路严格对齐与成对保存(新增)

**目标**:检出时保存"同一时刻"的可见光(带检测框)与红外(原始灰度)各一张,对齐误差尽量小;只保留最近 10 对;统计存图耗时。

**(1) 近期帧环形缓冲 —— 对齐的基础**

两个采集类除"最新帧"外,各自再维护一个轻量环形缓冲,保留最近若干帧(含时间戳):

```text
IR  ring:  最近 8 帧(覆盖 320ms,大于 10 个 40ms 帧间隔)
VIS ring:  最近 4 帧
```

- 帧内时间戳统一为采集/解码完成时刻的 `CLOCK_MONOTONIC_RAW`(IR 在 SDK 拉到帧时刻、VIS 在解码完成时刻),两路时钟同源可直接比较;
- 仅存指针/小结构,256×192 与 1280×720 的图像数据在 latest swap 时已持有,环形缓冲只记录最近帧的引用(实现上用 BgrFrame 拷贝 vector 也可,数据量小可接受)。

**(2) 最近邻配对(严格对齐策略)**

```text
触发时机:某可见光帧 V 经推理检出目标
配对:在 IR ring 中选取 |t_ir - t_V| 最小的帧 I
记录:align_delta_ms = |t_ir - t_V|
```

- 两相机均 25fps、且红外先启动出流,正常情况下 delta ≤ 半帧间隔(**≤20ms**),典型 5~10ms;
- 保存日志与退出汇总打印实际 delta(avg/max),作为对齐质量的量化依据;
- 若 delta > 40ms(红外卡顿/缓冲异常),照常保存但打印告警;
- 不采用"同时触发两路抓拍"(USB 设备不支持硬触发),最近邻 + 高帧率是软件方案中对齐最严格的做法;twocameraOnMAC 的 `LatestFrameSynchronizer`(直接各取最新)作为最简回退,本期用环形最近邻精度更高。

**(3) 成对文件命名与"按对清理"**

- 同一对共用同一时间戳前缀,一眼可辨成对:
  ```
  output/det_20260921_153000_123_vis.jpg   # 可见光 1280×720,带框+标签
  output/det_20260921_153000_123_ir.jpg    # 红外 256×192,原始
  ```
- 时间戳取自配对时刻(`gettimeofday` 毫秒),与第一期命名规则保持同源;
- 清理时**按前缀分组为"对"**,按时间序删除最旧的一对(两个文件一起 unlink),始终保留最近 **10 对(20 个文件)**;任何情况下不允许残留半对(删除时先删两个文件再计数,启动时若发现无配对的散文件也一并清掉)。

**(4) 存图耗时统计**

```text
t_save0: 画框开始前
  vis: 画框 → JPG 编码 → 写盘
  ir : JPG 编码 → 写盘
t_save1: 两个文件写完
save_ms = t_save1 - t_save0
```

- 两路编码写盘顺序执行(也可并行编码再写,先做顺序版,简单且耗时本就很小);
- 仅检出帧产生存图;每帧日志带 `save=4.6ms`,退出汇总给 save 的 avg/max(§12.3);
- `save_ms` 与 `infer` 分开统计,不混入推理耗时。

## 14. "红外优先"的保障措施

按成本从低到高排列,前两条为首版必做,其余为验证不达标时的兜底:

1. **架构隔离(必做)**:IR 独立采集线程,SDK 内部独立 USB 传输/缓冲,与可见光 V4L2、主线程推理完全不互相阻塞(§11)。
2. **启动顺序与校验(必做)**:严格按 camera_capture_test 验证过的顺序——先 `infrared.open()`(下发固件/校正表)+ `infrared.start()`(SDK ISO 出流),确认首窗 `cur` 达到 25fps 后再 open/start 可见光;可见光启动后若 IR 的 cur 跌破 24fps,打印告警并按第 3/4 条处理。
3. **红外采集线程提优先级(root 可用)**:`pthread_setschedparam` 设 `SCHED_RR`(低优先级值)或 `nice(-5)`,保证它在与 720p MJPG 软解争 CPU 时优先被调度;`uvc_frame_get()` 内部有超时,停止时 `uvc_camera_stream_close()` 会打断等待,退出响应不受影响。
4. **控制可见光 CPU 负载**:MJPG 解码已关闭 fancy upsampling/block smoothing;若 IR 仍受影响,可把可见光降为 640×480@25(命令行 `-W 640 -H 480`)或降帧,优先保 IR。
5. USB 层对启动顺序敏感(第 2 条);红外设备掉线恢复沿用 run.sh 机制,但注意 SDK 是 claim 原始 USB,恢复时需确保 SDK 完全关闭后再重枚举(§15)。

### 14.5 实测发现的 USB 带宽预留约束(2026-09-21 板端)

**拓扑**:两路相机与 r8152 网卡全部挂在同一个 EHCI USB2.0 总线(480Mbps,可用等时预算约 38MB/s)经外置 Hub 接入,板上只有一个 EHCI 控制器,无法换到不同总线。

**事实1:红外实际走组合流**。SDK 必须协商 `256×384 YUY2`(image+temp 上下拼接),`raw_data_cut` 再切出上半段 256×192;协商单高 256×192 流时 `uvc_frame_get` 快速返回空帧(raw_data_cut 报 data is NULL)。红外占用 4.9MB/s。

**事实2:可见光 STREAMON 报 `ENOSPC (No space left on device)`**。这是 uvcvideo 的 USB 带宽预留失败(不是磁盘空间)。MJPEG 设备按最坏情况(≈ 宽×高×2/帧)预留:1280×720@25 ≈ 46MB/s,与红外 4.9MB/s 相加超出总线预算。在同一进程连续多次启动后,连 640×480@25 也失败——怀疑 SDK 关闭流程未完全释放等时带宽(ghost reservation),需在每次关闭时彻底停流验证。

**应对(按优先级)**:
1. 关流使用 `uvc_camera_stream_close(CLOSE_CAM_SIDE_PREVIEW)`(而非 KEEP),并确保 `uvc_camera_close/release` 顺序执行,重启程序前后对比是否仍有残留;
2. 冷启动后、无任何历史运行的干净状态下实测单跑 1280×720@25 是否可通过(开机后第一次最接近真实预算);
3. 若 25fps 720p 确实超预算,与用户确认降级:优先 `1280×720@15` 或 `960×540@25`,再次 `640×480@25`(twocameraOnMAC 验证过可行);红外 25fps 始终不动;
